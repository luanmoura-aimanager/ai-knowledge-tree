A [transformation model](K5/transformation-as-code) that rebuilds its whole output
table on every run is simple and correct, and at some scale it becomes unaffordable.
If `fct_orders` has two years of history and one day of new orders arrives, rebuilding
recomputes two years to add one day. The work per run grows with the *total* table,
not with the *new* data, so a pipeline that started fast slowly chokes. The fix is to
process only the rows that are new or changed, and to fold them into the existing
table with a key-aware **merge** so a reprocessed batch updates the right row instead
of appending a duplicate<FN n="1" />.

## Full-refresh vs incremental

A **full-refresh** model drops the output and recreates it from the entire source
every run. Its cost is proportional to the accumulated table size $N$, regardless of
how little changed. An **incremental** model keeps the existing output and only reads,
transforms, and writes the new or changed source rows, $\Delta$ of them. Its cost is
proportional to $\Delta$. When new data trickles in against a large history,
$\Delta \ll N$ and the saving is the ratio $N / \Delta$.

The question incremental processing must answer is: *which rows are new or changed?*

## The high-water mark

The standard answer uses a monotically advancing column, typically an `updated_at`
timestamp the source stamps on every insert or update. The model records the maximum
value it has already processed, its **high-water mark** $w$. On the next run it selects
only source rows with `updated_at > w`, processes them, and advances $w$ to the new
maximum. Rows at or below $w$ were handled on a previous run and are skipped. The
high-water mark turns "which rows are new" into a single comparison.

## Merge semantics: insert new, update existing

Selecting the changed rows is half the job. Writing them is the other half, and a
plain append is wrong. If a row that already exists in the output was *updated* in the
source (same key, new values), appending it produces two rows for one key. The correct
write is a **merge** (also called **upsert**, from *update* + *insert*), keyed on a
stable identifier. For each incoming row with key $k$:

- **if $k$ is absent** in the target, **insert** the row;
- **if $k$ is present** in the target, **update** that row's columns to the incoming
  values.

The stable key is what makes this well-defined: it is the column (or set of columns)
that identifies the same logical entity across batches, the order id, the customer id.
Two rows with the same key are two versions of one entity, and the merge keeps the
latest.

This gives the property that makes reprocessing safe. Reapplying a batch that has
already been merged changes nothing: every key in it is present, so every row is an
update that overwrites a value with the identical value. A merge keyed on a stable id
is **idempotent**, which is precisely what lets a [retry or backfill](K5/scheduling-backfills)
rerun a batch without corrupting the table. Idempotent writes keyed on a stable id are
the standard defense against the duplicate delivery that stream and batch systems
cannot fully rule out<FN n="2" />.

## Worked example

Three batches arrive in sequence. Batches overlap on some keys: id 3 appears in
batches 1 and 2, id 2 in batches 1 and 3. The upsert keeps one row per id with the
latest value. The block then checks idempotency by reapplying the last batch, and
counts rows processed incrementally against a full-rebuild baseline.

```python
import numpy as np

# Three successive batches of (id, value). Some ids recur across batches.
batches = [
    np.array([(1, 100.0), (2, 200.0), (3, 300.0)], dtype=[("id", "i8"), ("val", "f8")]),
    np.array([(3, 350.0), (4, 400.0)],             dtype=[("id", "i8"), ("val", "f8")]),
    np.array([(2, 250.0), (5, 500.0)],             dtype=[("id", "i8"), ("val", "f8")]),
]

def upsert(table, batch):
    # Merge keyed on id: present key -> update, absent key -> insert.
    table = dict(table)
    for rid, val in zip(batch["id"], batch["val"]):
        table[int(rid)] = float(val)
    return table

# Incremental: fold each batch in, counting only the rows we actually touch.
table = {}
rows_incremental = 0
for b in batches:
    table = upsert(table, b)
    rows_incremental += b.size

# Full-rebuild baseline: each run reprocesses the entire accumulated source so far.
rows_full = 0
seen = 0
for b in batches:
    seen += b.size
    rows_full += seen

final = dict(sorted(table.items()))
print("final table:", final)
print("rows processed  incremental:", rows_incremental)
print("rows processed  full-rebuild:", rows_full)

# One row per id, each holding the LATEST value (id 2 -> 250, id 3 -> 350).
assert len(final) == 5
assert final[2] == 250.0 and final[3] == 350.0
assert final == {1: 100.0, 2: 250.0, 3: 350.0, 4: 400.0, 5: 500.0}

# Idempotent: re-applying an already-merged batch leaves the table unchanged.
table_again = upsert(table, batches[-1])
assert table_again == table

# Incremental touched far fewer rows than rebuilding every run.
assert rows_incremental == 7 and rows_full == 15
assert rows_incremental < rows_full
print("incremental, idempotent, cheaper:", True)
```

The merge keeps one row per id with the latest value, reprocessing the last batch is a
no-op, and incremental touched 7 rows where full-rebuild touched 15.

## Exercises

**Exercise 1.** A `fct_orders` table holds $N = 730{,}000$ rows of accumulated
history. Each daily run adds $\Delta = 1{,}000$ new or changed rows. Compute the rows
processed by a full-refresh run and by an incremental run, and the saving ratio. Then
state in words how each cost scales as the table keeps growing.

<details>
<summary>Solution</summary>

**Step 1.** A full-refresh model recreates the output from the entire source, so its
cost is proportional to the accumulated size: it processes all $N = 730{,}000$ rows.

**Step 2.** An incremental model reads, transforms, and writes only the new or changed
rows: it processes $\Delta = 1{,}000$ rows.

**Step 3.** The saving is the ratio

$$
\frac{N}{\Delta} = \frac{730{,}000}{1{,}000} = 730,
$$

so the incremental run does $1/730$ of the work.

**Step 4.** Full-refresh cost grows with $N$: as history accumulates, each run gets
strictly more expensive even though the daily $\Delta$ is unchanged. Incremental cost
stays proportional to $\Delta$, so it is flat as long as the daily change volume is
flat, independent of how large the history grows.

</details>

**Exercise 2.** A merge keyed on a stable id is **idempotent**: reapplying an
already-merged batch changes nothing. Prove this from the merge rule (absent key
inserts, present key updates), and explain why this is exactly the property a retry or
backfill needs.

<details>
<summary>Solution</summary>

**Step 1.** Take a batch $B$ already merged into target $T$, giving $T' = \text{merge}(T, B)$.
Every key $k$ in $B$ is present in $T'$ with $T'$'s value equal to $B$'s value, because
the first merge either inserted $k$ from $B$ or updated $k$ to $B$'s value.

**Step 2.** Apply $B$ again to $T'$. For each key $k$ in $B$: $k$ is present in $T'$, so
the rule updates $k$'s columns to $B$'s values. But $T'$ already holds exactly $B$'s
values for those columns, so the update overwrites each value with the identical value.
No key is inserted (all are present) and no value changes.

**Step 3.** Therefore $\text{merge}(T', B) = T'$: the second application is a no-op, the
definition of idempotence.

**Step 4.** A retry reruns the same batch after a failure, and a backfill may re-touch a
batch already processed. Idempotence guarantees each such rerun lands the table in the
same state as a single clean run, so reruns cannot duplicate rows or double-count. This
is the standard defense against the duplicate delivery batch and stream systems cannot
fully rule out.

</details>

**Exercise 3 (code).** Implement high-watermark selection over a stream of source rows
stamped with an `updated_at` integer. Starting from watermark $w = 0$, process rows
with `updated_at > w` in two runs, advancing $w$ to the new maximum each time. Assert
that each row is processed exactly once across the two runs and that the final
watermark equals the global maximum.

<details>
<summary>Solution</summary>

```python
import numpy as np

rng = np.random.default_rng(0)
# Source rows: (id, updated_at). updated_at is a monotone version stamp.
n = 12
ids = np.arange(n)
updated_at = np.sort(rng.integers(1, 100, size=n))   # ascending stamps
source = np.rec.fromarrays([ids, updated_at], names=["id", "updated_at"])

def run(source, w):
    # Select only rows strictly above the high-water mark.
    mask = source["updated_at"] > w
    selected = source[mask]
    new_w = int(selected["updated_at"].max()) if selected.size else w
    return selected, new_w

# Split the stamp range so run 1 sees an early slice, run 2 sees the rest.
mid = int(np.median(source["updated_at"]))

# Run 1: watermark starts at 0, but cap the visible source at `mid` to model
# rows that have not yet arrived.
w = 0
arrived_1 = source[source["updated_at"] <= mid]
sel_1, w = run(arrived_1, w)

# Run 2: now all rows have arrived; select only those above the advanced watermark.
sel_2, w = run(source, w)

processed_ids = np.concatenate([sel_1["id"], sel_2["id"]])

# Every source row processed exactly once (no row skipped, none reprocessed).
assert np.array_equal(np.sort(processed_ids), ids)
assert len(processed_ids) == n
# Final watermark is the global maximum stamp.
assert w == int(source["updated_at"].max())
print("processed:", len(processed_ids), "rows once; final watermark:", w)
```

The high-water mark turns "which rows are new" into the single comparison
`updated_at > w`; across the two runs every row is selected once and the watermark
climbs to the global maximum.

</details>

Idempotency here
was a property of one table's merge; the [next lesson](K5/scheduling-backfills) lifts
it to the schedule, where time-partitioned runs and backfills demand that *every* task
be safe to rerun.
