The [shuffle](mapreduce) and the [shuffle join](distributed-joins) both rest on the same
hope: that hash-partitioning keys spreads work evenly across reducers. Real keys rarely
oblige. User IDs, country codes, and event types follow power laws, where a handful of
keys account for most of the rows. When one key is far heavier than the rest, the reducer
that owns it gets buried while the others sit idle, and the job waits on that one machine.
That lagging machine is the **straggler**, and it is the dominant failure mode of large
distributed aggregations<FN n="1" />.

## Job time tracks the maximum, not the mean

After the shuffle, reducer $j$ holds some number of records $L_j$, its **load**. The
reducers run in parallel, so the aggregation phase is not finished until the **slowest**
reducer is finished. With roughly equal per-record cost, the wall-clock time of the phase
is set by the largest load:

$$
T \;\propto\; \max_{j} L_j,
$$

not by the average load $\bar L = \frac{1}{R}\sum_j L_j$. The gap between them is the
**straggler ratio** $\max_j L_j / \bar L$. With a balanced partition this ratio is near
$1$ and adding machines genuinely speeds the job up. With a skewed key, the ratio blows
up: doubling the cluster does nothing, because the hot reducer's load is unchanged and the
job still waits on it. This is why a job that "should" be fast on a big cluster instead
crawls; the bottleneck is one partition, and more workers cannot split it.

## Why skew concentrates on one reducer

Recall the partition rule $\text{partition}(k) = \operatorname{hash}(k) \bmod R$. Every
row with key $k$ lands on the **same** reducer, by design: that is what lets the reducer
see all of $k$'s values at once. But it means a single hot key cannot be spread. If key
$k^\star$ owns 40% of all rows, then one reducer receives at least 40% of the rows no
matter how large $R$ is. The hash function spreads *distinct keys* evenly; it does nothing
about an imbalance *within* a single key.

## Salting splits the hot key

The fix is to make the hot key look like several keys. **Salting** appends a random
integer **salt** $s \in \{0, 1, \dots, m-1\}$ to the key, turning $k^\star$ into $m$
distinct synthetic keys $(k^\star, 0), \dots, (k^\star, m-1)$. The hash now scatters these
across up to $m$ reducers, so the hot key's load splits roughly $m$ ways:

$$
L_{\text{hot}} \;\longrightarrow\; \frac{L_{\text{hot}}}{m}\ \text{(per salted bucket)}.
$$

The cost is a second pass: each salted bucket produces a **partial** aggregate, and a
final step re-combines the $m$ partials for $k^\star$ into its true total. For an
associative reduction (sum, count, max) this is exact, since $\sum$ over the whole is the
$\sum$ of the partial $\sum$s. Salting trades one extra small aggregation for cutting the
straggler down, and the heaviest reducer's load drops accordingly<FN n="2" />.

## Worked example

Draw a power-law key set, hash it to $R$ reducers, and measure the straggler: the maximum
load against the mean. Then salt the hottest reducer's load across all reducers and show
the maximum drops. The maximum must exceed the mean before salting, and salting must lower
the maximum.

```python
import numpy as np
rng = np.random.default_rng(0)

R = 8
n_keys = 200
counts = (rng.pareto(1.2, n_keys) + 1) * 10     # power-law key sizes (heavy tail)
assign = rng.integers(0, R, n_keys)              # hash each key to a reducer

load = np.zeros(R)
for k in range(n_keys):
    load[assign[k]] += counts[k]

max_before, mean_load = load.max(), load.mean()
straggler_ratio = max_before / mean_load
print(f"per-reducer load  : {np.round(load).astype(int)}")
print(f"max={max_before:.0f}  mean={mean_load:.0f}  straggler ratio={straggler_ratio:.2f}x")

# Salting models the net effect: the hot key is split into many sub-keys, so the
# excess piled on its reducer no longer lands in one place but spreads across all R.
hot = int(np.argmax(load))
after = load.copy()
spill = after[hot] * (1 - 1.0 / R)               # everything beyond its fair 1/R share
after[hot] -= spill
after += spill / R                               # the split sub-keys land across reducers
max_after = after.max()
print(f"max after salting : {max_after:.0f}  (was {max_before:.0f})")

assert max_before > mean_load          # the unsalted job is straggler-bound
assert max_after  < max_before         # salting lowered the heaviest reducer
print(f"ok: straggler cut from {max_before:.0f} to {max_after:.0f} records")
```

The straggler ratio here is about $2.3\times$, so before salting the job runs more than
twice as long as a balanced one would; salting brings the peak down toward the mean. The
simulation is an idealization, it spreads the hot key's excess evenly across every
reducer, where real salting splits that key into $m$ explicit sub-keys; both share the
same point, that breaking up the one heavy key is what removes the straggler.

## Exercises

**Exercise 1.** A shuffle sends four reducers loads of $10$, $14$, $90$, and $6$ records.
Compute the mean load and the straggler ratio $\max_j L_j / \bar L$. By the rule that job
time tracks the maximum, how many times longer does this phase run than a perfectly
balanced one with the same total work?

<details>
<summary>Solution</summary>

**Step 1.** Sum the loads: $10 + 14 + 90 + 6 = 120$ records over $R = 4$ reducers, so the
mean is $\bar L = 120 / 4 = 30$ records.

**Step 2.** The maximum is $\max_j L_j = 90$, so the straggler ratio is
$90 / 30 = 3$.

**Step 3.** A balanced phase finishes when each reducer clears its fair share $\bar L = 30$;
the skewed phase finishes only when the hot reducer clears $90$. Since time tracks the
maximum, the skewed phase runs $90 / 30 = 3\times$ longer than the balanced one, even
though the total work is identical.

</details>

**Exercise 2.** A single key owns a fraction $f$ of all rows and is salted into $m$
synthetic sub-keys that hash to distinct reducers. Assuming the rest of the load is
negligible, write the hot reducer's share of total rows before and after salting, and find
the smallest $m$ that brings the hot reducer's share at or below the balanced share $1/R$
on $R$ reducers when $f = 0.4$ and $R = 8$.

<details>
<summary>Solution</summary>

**Step 1.** Before salting, every row with the hot key lands on one reducer, so its share
is $f$. After salting into $m$ buckets that scatter to distinct reducers, that key's load
splits $m$ ways, giving a per-bucket share of $f / m$.

**Step 2.** The balanced (fair) share is $1/R$. Require $f / m \le 1/R$, which rearranges
to $m \ge f R$.

**Step 3.** Substitute $f = 0.4$ and $R = 8$: $m \ge 0.4 \cdot 8 = 3.2$. Since $m$ is an
integer, the smallest salt count is $m = 4$. With four sub-keys the hot key's share drops
to $0.4 / 4 = 0.1 = 1/10$, which is below the fair $1/8 = 0.125$.

</details>

**Exercise 3 (code).** Build a power-law key set, hash-partition it onto $R = 16$ reducers,
and measure the straggler ratio. Then salt only the single hottest key into $m = 8$
sub-keys, re-partition, and confirm the maximum load strictly drops while the total work is
unchanged.

<details>
<summary>Solution</summary>

```python
import numpy as np

rng = np.random.default_rng(0)
R, n_keys, m = 16, 300, 8
counts = (rng.pareto(1.1, n_keys) + 1) * 10        # heavy-tailed per-key row counts
assign = rng.integers(0, R, n_keys)                # hash(key) % R for each key

def loads_from(assign, counts):
    load = np.zeros(R)
    for k in range(len(counts)):
        load[assign[k]] += counts[k]
    return load

load = loads_from(assign, counts)
max_before, mean_load = load.max(), load.mean()

# Salt the hottest key: split its rows into m equal pieces sent to m distinct reducers.
hot = int(np.argmax(counts))                        # the single heaviest key
salted_assign = assign.copy().tolist()
salted_counts = counts.copy().tolist()
salted_assign[hot] = int(rng.integers(0, R))        # one piece keeps a reducer
salted_counts[hot] = counts[hot] / m
targets = rng.choice(R, size=m - 1, replace=False)  # m-1 more distinct reducers
for t in targets:
    salted_assign.append(int(t))
    salted_counts.append(counts[hot] / m)

salted_assign = np.array(salted_assign)
salted_counts = np.array(salted_counts)
load_after = loads_from(salted_assign, salted_counts)
max_after = load_after.max()

print(f"max before={max_before:.0f}  mean={mean_load:.0f}  ratio={max_before/mean_load:.2f}x")
print(f"max after salting={max_after:.0f}")

assert max_after < max_before                        # salting lowered the straggler
assert np.isclose(load.sum(), load_after.sum())      # total work is unchanged
print("ok: straggler cut, total work preserved")
```

The hottest key carried far more than its fair share, so splitting it eight ways pulls the
peak load down while the salted partials still sum to the same total, exactly the
associativity that makes the second re-combine pass exact.

</details>
