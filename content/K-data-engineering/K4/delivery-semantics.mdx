A consumer reads an event from a [partition](K4/log-and-kafka), processes it, and
[commits its offset](K4/log-and-kafka) so it does not read that event again. Now
the machine crashes between processing and committing. On restart the consumer
re-reads from the last committed offset, which is *before* the event it already
processed, and processes it a second time. Or suppose it committed *first* and
crashed before processing; on restart it skips the event entirely. The order of
those two steps, process and commit, decides whether failures **lose** events or
**duplicate** them, and that choice is the **delivery semantics** of the pipeline<FN n="1" />.

## Three guarantees

Across a producer, the [log](K4/log-and-kafka), and a consumer, a pipeline offers
one of three guarantees about how many times each event is processed:

- **At-most-once.** Each event is processed zero or one times: never duplicated, but
  it **may be lost**. This is what *commit-then-process* gives, the offset advances
  first, so a crash before processing skips the event. Cheapest and lowest latency
  (no retries, no dedup state), acceptable only when an occasional dropped event is
  harmless, like a sampled metric.
- **At-least-once.** Each event is processed one or more times: never lost, but it
  **may be duplicated**. This is *process-then-commit*, the work happens first, so a
  crash before the commit causes a re-read and reprocessing. It is the cheap,
  default workhorse, because retrying until you see an acknowledgement is easy. The
  cost is duplicates.
- **Exactly-once.** Each event affects the result exactly once: neither lost nor
  duplicated. This is what everyone wants and what is expensive to provide in
  general, because making the *processing side effect* and the *offset commit* atomic
  across machines requires distributed transactions (two-phase commit, transactional
  writes), which add coordination, latency, and operational fragility.

The practical tension: at-most-once is too lossy for anything that touches money or
state, and true end-to-end exactly-once is heavyweight. The escape hatch is to take
cheap at-least-once delivery and make the *duplicates harmless*.

## Idempotency turns at-least-once into effectively-once

An operation is **idempotent** when applying it more than once has the same effect
as applying it once. Formally, for an update $f$ applied to state, idempotence means

$$
f(f(x)) = f(x).
$$

"Set the balance to \$100" is idempotent: doing it twice leaves the balance at \$100.
"Add \$100 to the balance" is **not**: doing it twice adds \$200. Counting events is
the non-idempotent case, a `count += 1` per delivery over-counts every duplicate,
which is exactly the failure mode of at-least-once.

The fix is to make the consumer idempotent on its own by **deduplicating on a stable
event id**. Every event carries a unique id (assigned at the source, not at
delivery). The consumer keeps a set of ids it has already applied; on each delivery
it checks membership first:

$$
\text{apply}(e) \;=\;
\begin{cases}
\text{process } e,\ \text{add } e.\text{id to } \texttt{seen} & e.\text{id} \notin \texttt{seen} \\[4pt]
\text{skip (already applied)} & e.\text{id} \in \texttt{seen}
\end{cases}
$$

A redelivered event has an id already in `seen`, so it is skipped, and the second
application is a no-op. The dedup check makes the whole consumer idempotent, so
**at-least-once delivery plus an idempotent consumer equals effectively-once
processing**, at the cost of storing the set of seen ids rather than a distributed
transaction<FN n="2" />. The win is that the hard part (exactly-once *delivery*) is replaced by
the easy part (cheap delivery + a dedup set), and the result is the same.

## Worked example

Simulate at-least-once delivery: 1000 distinct events, of which a random ~18% get
redelivered once. A naive counter increments per delivery and over-counts; an
idempotent consumer keyed on the event id counts each distinct event once. The
asserts pin both outcomes: naive overshoots the truth, idempotent hits it exactly.

```python
import numpy as np
rng = np.random.default_rng(0)

true_n = 1000
ids = np.arange(true_n)                       # the distinct event ids
dup_mask = rng.random(true_n) < 0.18          # ~18% get redelivered once
stream = np.concatenate([ids, ids[dup_mask]]) # at-least-once: originals + duplicates
rng.shuffle(stream)                           # duplicates arrive interleaved

# Naive consumer: one increment per delivery (non-idempotent count += 1).
naive_count = stream.size

# Idempotent consumer: dedup on the event id (process only first sighting).
seen = set()
idempotent_count = 0
for eid in stream:
    if eid not in seen:                       # f(f(x)) == f(x): re-applying is a no-op
        seen.add(int(eid))
        idempotent_count += 1

print("true       :", true_n)
print("naive      :", naive_count)
print("idempotent :", idempotent_count)

# At-least-once duplicates make the naive count overshoot the truth.
assert naive_count > true_n
# Dedup on a stable id recovers the true count exactly: effectively-once.
assert idempotent_count == true_n
print("over-count =", naive_count - true_n, "duplicates absorbed by dedup")
```

The naive counter reports 1160 against a true 1000, while the idempotent consumer
reports exactly 1000: the duplicates from cheap at-least-once delivery are absorbed
by the dedup set.

## Exercises

**Exercise 1.** A consumer reads each event, processes it, then commits its offset.
For each of the two orderings below, classify the delivery semantics and say
whether a crash at the worst moment loses or duplicates an event: (a)
process-then-commit; (b) commit-then-process. Then explain why no ordering of just
these two steps can give exactly-once.

<details>
<summary>Solution</summary>

**Step 1.** Process-then-commit. The work happens, then the offset advances. A
crash after processing but before the commit leaves the offset pointing *before* the
event, so on restart the event is re-read and processed again. Nothing is skipped.
This is **at-least-once**: events may be duplicated, never lost.

**Step 2.** Commit-then-process. The offset advances first, then the work happens. A
crash after the commit but before processing leaves the offset *past* an event whose
work never ran, so on restart it is skipped. This is **at-most-once**: events may be
lost, never duplicated.

**Step 3.** Why neither gives exactly-once. The processing side effect and the
offset commit are two writes to two different systems (the sink and the offset
store) with no shared transaction. Whichever you do first, a crash in the gap
between them exposes the other as not-yet-done, producing either a duplicate or a
loss. Closing the gap requires making the two atomic across machines (a distributed
transaction), which is precisely the expensive coordination exactly-once needs and
that mere ordering cannot supply.

</details>

**Exercise 2.** Classify each operation as idempotent or not, using the definition
$f(f(x)) = f(x)$, and justify: (a) `SET balance = 100`; (b) `balance += 100`; (c)
`INSERT ... ON CONFLICT (id) DO NOTHING`; (d) `counter = counter + 1`. For the
non-idempotent ones, state the dedup mechanism that makes redelivery safe.

<details>
<summary>Solution</summary>

**Step 1.** (a) `SET balance = 100` is idempotent. Applying it once sets 100;
applying it again sets 100. $f(f(x)) = f(100) = 100 = f(x)$. A redelivery is a
no-op by construction.

**Step 2.** (b) `balance += 100` is not idempotent. Once gives $x + 100$; twice
gives $x + 200 \ne x + 100$. (d) `counter = counter + 1` is the same shape: each
delivery over-counts, which is the canonical at-least-once failure.

**Step 3.** (c) `INSERT ... ON CONFLICT (id) DO NOTHING` is idempotent on the row
keyed by `id`. The first insert lands; a second insert with the same `id` conflicts
and is dropped, leaving the table unchanged. $f(f(x)) = f(x)$.

**Step 4.** Making the non-idempotent operations safe. Wrap them in a dedup on a
stable, source-assigned event id: keep a `seen` set (or a unique key in the sink),
and apply the increment only when the id is not already present. The first sighting
runs `+= 100` or `+= 1`; every redelivery finds the id in `seen` and skips, turning
at-least-once delivery into effectively-once processing.

</details>

**Exercise 3 (code).** Simulate at-least-once delivery where each event can be
redelivered *more than once* (not just once). Generate 2000 distinct events; give
each a random number of extra deliveries drawn so the duplicate rate is heavy.
Count three ways: the true distinct count, a naive per-delivery counter, and an
idempotent consumer that dedups on the event id. Assert the naive counter strictly
overshoots and the idempotent counter recovers the truth exactly.

<details>
<summary>Solution</summary>

```python
import numpy as np
rng = np.random.default_rng(0)

true_n = 2000
ids = np.arange(true_n)                          # the distinct event ids

# At-least-once with heavy redelivery: each event delivered 1 + k times,
# k ~ Poisson, so many events arrive several times over.
extra = rng.poisson(0.7, true_n)                 # extra deliveries per event
stream = np.repeat(ids, 1 + extra)               # originals plus their duplicates
rng.shuffle(stream)                              # duplicates interleave with originals

# Naive consumer: count += 1 per delivery (non-idempotent).
naive_count = stream.size

# Idempotent consumer: dedup on the event id; only the first sighting counts.
seen = set()
idempotent_count = 0
for eid in stream:
    if eid not in seen:                          # f(f(x)) == f(x): redelivery is a no-op
        seen.add(int(eid))
        idempotent_count += 1

print("true       :", true_n)
print("naive      :", naive_count)
print("idempotent :", idempotent_count)
print("over-count :", naive_count - true_n)

# Heavy redelivery makes the naive count strictly overshoot the truth.
assert naive_count > true_n
# Dedup on a stable id recovers the true distinct count exactly: effectively-once.
assert idempotent_count == true_n
```

The naive counter inflates with every redelivery, while the idempotent consumer
keyed on the event id absorbs all of them and lands exactly on 2000, the same result
exactly-once delivery would give, without any distributed transaction.

</details>
