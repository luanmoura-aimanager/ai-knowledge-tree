[Windowing](K4/windowing) assigned every event to a window using the event's own
timestamp, and quietly assumed events arrive in timestamp order. In a real stream
they do not. A phone goes through a tunnel, buffers its events, and uploads them
five minutes later; a [partition](K4/log-and-kafka) is briefly slow. So an event
that *happened* at 12:00 can *arrive* at 12:05, after the noon window looked done
and was already aggregated. The system needs a principled answer to one question:
when is it safe to declare a window complete and emit its result, knowing a
straggler might still be in flight? The **watermark** is that answer<FN n="1" />.

## Two clocks: event time and processing time

Every event has two timestamps, and keeping them apart is the whole game.

- **Event time** $t_e$: when the event actually occurred, stamped at the source
  (the moment the user clicked). This is the time the *windows* are defined in,
  because the metric ("clicks in the noon hour") is about when things happened.
- **Processing time** $t_p$: when the event arrived at the stream processor and got
  handled. This is the clock on the server doing the work.

If the network were instant and ordered, $t_p = t_e$ for every event and the two
clocks would coincide. They never do. The delay $t_p - t_e \ge 0$ varies per event,
and because it varies, events arrive **out of order in event time**: the processor
can see an event with $t_e = 12:05$ and then, later in processing time, an event
with $t_e = 12:00$. A window keyed on event time therefore cannot close just because
the wall clock passed its end; some of its events may not have arrived yet.

## The watermark

A **watermark** is the processor's running assertion: *"I believe I have now seen
every event with event time at or before $W$."* It is a value on the event-time axis
that only moves forward, and the standard way to compute it is to take the largest
event time seen so far and subtract a fixed **allowed lateness** $L \ge 0$:

$$
W(t_p) = \max_{\text{events seen by } t_p} t_e \;-\; L.
$$

Read it as a heuristic with a safety margin. The largest event time seen,
$\max t_e$, is the front of the stream; subtracting $L$ pulls the watermark back so
that an event arriving up to $L$ behind the front is still considered on time. Two
rules hang off the watermark:

- **A window $[a, b)$ fires when $W(t_p) \ge b$.** Once the watermark passes the
  window's end, the processor declares the window complete, computes its aggregate,
  and emits it. The window stops accepting input.
- **An event is late, and dropped, when $t_e < W(t_p)$ at arrival.** Its window has
  already fired (the watermark is past $t_e$, hence past that window's end), so the
  result was already emitted. Production systems either drop such events or route
  them to a **side output** for separate, slower reconciliation<FN n="2" />.

This is purely a bound, not a guarantee: $\max t_e - L$ is a guess that no event is
more than $L$ behind the front. A truly pathological straggler still violates it,
which is exactly why genuinely late events exist and have to be handled.

## The tradeoff that $L$ sets

The allowed lateness $L$ is the one knob, and it trades **completeness against
latency** directly.

- **Larger $L$** pulls the watermark further back, so windows wait longer before
  firing and catch more stragglers. More events are counted (higher completeness),
  but every result is delayed by up to $L$ (higher latency).
- **Smaller $L$** fires windows sooner, so results are fresh, but any event slower
  than $L$ misses its window and is dropped (lower completeness).

So the count of dropped-late events is **monotonically non-increasing in $L$**:
raising $L$ can only rescue events that a smaller $L$ would have dropped, never
create new late ones. That monotonicity is the property the worked example checks.

## Worked example

Build a stream of 40 events with random processing delays (a few badly delayed), sort
them into arrival order, and track the watermark as each arrives. For a given allowed
lateness $L$, an event is late when its event time is already below the watermark at
the moment it arrives. The assert confirms the monotonic tradeoff: increasing $L$
never increases the number of dropped-late events.

```python
import numpy as np
rng = np.random.default_rng(0)

n = 40
event_time = np.sort(rng.uniform(0, 20, n))   # when each event happened
delay = rng.exponential(1.2, n)               # network/processing delay
delay[[7, 19, 31]] += 6.0                     # three badly delayed stragglers
proc_time = event_time + delay                # when it arrived

order = np.argsort(proc_time)                 # replay in arrival order
et = event_time[order]
# Watermark just before each arrival = max event time among already-arrived events,
# minus L. max(event_time) over arrivals is a running max in arrival order.
running_max = np.maximum.accumulate(et)

def dropped_late(L):
    watermark = running_max - L               # watermark at each arrival
    return int(np.sum(et < watermark))        # events older than the watermark

for L in [0.0, 1.0, 2.0, 5.0]:
    print(f"L = {L:>3}  ->  dropped late = {dropped_late(L)}")

counts = [dropped_late(L) for L in [0.0, 1.0, 2.0, 3.0, 5.0, 8.0]]
# Completeness vs latency: more allowed lateness can only drop fewer (never more).
assert all(counts[i] >= counts[i + 1] for i in range(len(counts) - 1))
assert dropped_late(0.0) > dropped_late(5.0)
print("dropped counts by L:", counts, "-> monotonically non-increasing")
```

With $L = 0$ the watermark hugs the front of the stream and many out-of-order events
are dropped; raising $L$ widens the grace period and the dropped count falls to a
handful and then to zero.

## Exercises

**Exercise 1.** Events arrive in processing-time order with event times (in
minutes) $12, 18, 15, 25, 22, 30$. The allowed lateness is $L = 4$. Using
$W = \max t_e \text{ seen so far} - L$, compute the watermark just before each
arrival and decide whether each event is late (an event is late when
$t_e < W$ at the moment it arrives). Which window does the late event belong to,
and was that window already fired? Use tumbling windows of width 10 starting at 0.

<details>
<summary>Solution</summary>

**Step 1.** Track the running max of event times in arrival order and subtract
$L = 4$ to get the watermark at each arrival, then compare the arriving $t_e$ to it.

| arrival | $t_e$ | running max before | $W = \max - 4$ | late? ($t_e < W$) |
|---|---|---|---|---|
| 1 | 12 | $-\infty$ | $-\infty$ | no |
| 2 | 18 | 12 | 8 | no |
| 3 | 15 | 18 | 14 | no ($15 \ge 14$) |
| 4 | 25 | 18 | 14 | no |
| 5 | 22 | 25 | 21 | no ($22 \ge 21$) |
| 6 | 30 | 25 | 21 | no |

**Step 2.** With $L = 4$, no event is late: every arriving event time stays at or
above the watermark. The closest call is event 3 ($t_e = 15$ against $W = 14$) and
event 5 ($t_e = 22$ against $W = 21$), both on time by a margin of 1.

**Step 3.** Tighten to see the boundary. With $L = 2$, before arrival 3 the
watermark is $18 - 2 = 16$, and $t_e = 15 < 16$, so event 3 would be late. It
belongs to the tumbling window $[10, 20)$ (since $\lfloor 15 / 10 \rfloor = 1$). At
that point the watermark 16 has not yet reached the window end 20, so the window had
*not* fired and the event would still make it in; it is only "late" relative to the
watermark heuristic. This shows the count of late events depends on $L$, the point
the next exercise pins numerically.

</details>

**Exercise 2.** Prove that the number of dropped-late events is monotonically
non-increasing in the allowed lateness $L$: for $L_1 \le L_2$, raising $L$ from
$L_1$ to $L_2$ can never increase the count of dropped events. Argue per event.

<details>
<summary>Solution</summary>

**Step 1.** Fix one event with event time $t_e$ arriving at some processing time,
when the running max of seen event times is $M$. The watermark at that instant is
$W(L) = M - L$. The event is dropped as late exactly when $t_e < W(L)$, i.e.
$t_e < M - L$.

**Step 2.** Compare the two latenesses on this single event. With $L_1 \le L_2$ we
have $M - L_2 \le M - L_1$, so $W(L_2) \le W(L_1)$: the larger $L$ produces a lower
(further-back) watermark at the same instant. If the event is not dropped under
$L_1$ (meaning $t_e \ge M - L_1$), it is also not dropped under the lower bar
$M - L_2$, since $t_e \ge M - L_1 \ge M - L_2$.

**Step 3.** So no event that survived at $L_1$ becomes dropped at $L_2 \ge L_1$.
The dropped set under $L_2$ is a subset of the dropped set under $L_1$ (the running
max $M$ at each arrival depends only on arrival order, not on $L$). Hence the dropped
count is non-increasing in $L$. This is the completeness-versus-latency trade: a
larger $L$ can only rescue stragglers, never create new late events, at the cost of
delaying every window's firing by up to $L$.

</details>

**Exercise 3 (code).** Build a stream of 60 events with random processing delays
and a few heavy stragglers. Replay them in arrival order, advance the watermark as
$\max t_e \text{ seen} - L$, and count dropped-late events for a sweep of $L$
values. Verify numerically that the dropped count is monotonically non-increasing
in $L$ and that $L = 0$ drops strictly more than a large $L$.

<details>
<summary>Solution</summary>

```python
import numpy as np
rng = np.random.default_rng(0)

n = 60
event_time = np.sort(rng.uniform(0, 30, n))      # when each event happened
delay = rng.exponential(1.0, n)                  # network / processing delay
delay[[9, 23, 41, 55]] += 7.0                    # heavy stragglers
proc_time = event_time + delay                   # when it arrived

order = np.argsort(proc_time)                     # replay in arrival order
et = event_time[order]
running_max = np.maximum.accumulate(et)           # max event time seen so far

def dropped_late(L):
    watermark = running_max - L                   # watermark just before each arrival
    return int(np.sum(et < watermark))            # arrivals older than the watermark

Ls = [0.0, 0.5, 1.0, 2.0, 4.0, 8.0]
counts = [dropped_late(L) for L in Ls]
for L, c in zip(Ls, counts):
    print(f"L = {L:>4}  ->  dropped late = {c}")

# Completeness vs latency: raising L can only drop fewer (never more).
assert all(counts[i] >= counts[i + 1] for i in range(len(counts) - 1))
# A zero grace period drops strictly more than a generous one.
assert dropped_late(0.0) > dropped_late(8.0)
```

The dropped count falls as $L$ rises and never climbs, confirming the per-event
monotonicity argument: a wider grace period rescues stragglers and drops a subset of
what a tighter one drops.

</details>

Even at-least-counted events can still arrive twice, which
raises the orthogonal question of how many times each event is *delivered* in the
first place. That is [delivery semantics](K4/delivery-semantics).
