Serving a model is answering requests under two competing pressures: each request
should return *fast* (low **latency**), and the system should handle *many*
requests per second (high **throughput**). These pull in opposite directions, and
the main knob that trades one for the other is **batching**. To reason about the
trade you need three tools: percentiles to describe latency honestly, Little's law
to relate the quantities, and the batching curve itself.

## Latency is a distribution, so use percentiles

The latency of a service is not one number; it is a distribution over requests,
and a heavily right-skewed one (most requests are quick, a few are slow because of
queueing, garbage collection, or a cold cache). Reporting the **mean** hides the
slow tail, and the tail is what users feel. So latency is summarized by
**percentiles**: the $p$-th percentile is the value below which $p\%$ of requests
fall. **p50** (the median) is the typical experience; **p99** is the tail, the
latency that the slowest $1\%$ exceed. On a skewed distribution $p99$ can be many
times the mean, which is exactly why service targets are written against $p99$,
not the average: optimizing the average can leave a miserable tail untouched.

## Little's law

The three quantities are tied together by **Little's law**, a result that holds
for any stable queueing system regardless of its internals<FN n="1" />. Let $L$ be the average
number of requests *in the system* at once (the concurrency), $\lambda$ the average
**throughput** (requests arriving and completing per second), and $W$ the average
**latency** (time a request spends in the system). Then

$$
L = \lambda \, W.
$$

The intuition is a flow balance: if requests leave at rate $\lambda$ and each spent
time $W$ inside, then at any instant the ones still in the system are those that
arrived in the last $W$ seconds, about $\lambda W$ of them. The law is the
capacity-planning workhorse: it lets you compute the concurrency a service must
sustain ($L = \lambda W$) from a target throughput and measured latency, or invert
it to find what latency a fixed concurrency budget allows.

## The batching tradeoff

A model server can process requests one at a time or **batch** several into one
forward pass. Batching wins on throughput because a forward pass has a fixed
overhead (launching the computation, loading weights) that is amortized over the
batch. Model the time to process a batch of size $b$ as

$$
T(b) = c_0 + c_1 b,
$$

a fixed cost $c_0$ plus a per-request cost $c_1$. Throughput is the batch divided
by its time,

$$
\text{throughput}(b) = \frac{b}{T(b)} = \frac{b}{c_0 + c_1 b},
$$

which **increases** with $b$ toward the ceiling $1/c_1$ as the fixed cost is spread
ever thinner. But a request in a batch waits for the whole batch to finish, so its
latency is about $T(b)$, which **increases** with $b$. Bigger batches buy
throughput and pay in latency<FN n="2" />. The serving engineer's job is to choose the largest
batch whose $T(b)$ still fits inside the $p99$ latency target, which is precisely
the tension that [LLM serving](llm-serving) must manage dynamically.

## Worked example

We summarize a skewed latency sample with percentiles, apply Little's law, and
trace throughput and latency as the batch size grows.

```python
import numpy as np
rng = np.random.default_rng(0)

# Right-skewed latency sample (ms): mean is pulled below the p99 tail.
lat = rng.gamma(shape=2.0, scale=20.0, size=100_000)
p50, p95, p99 = np.percentile(lat, [50, 95, 99])
print(f"mean={lat.mean():.1f}ms  p50={p50:.1f}ms  p95={p95:.1f}ms  p99={p99:.1f}ms")
assert p99 > 2 * lat.mean()                      # the tail dwarfs the average

# Little's law: concurrency needed to sustain a throughput at a given latency.
lam, W = 200.0, 0.05                              # 200 req/s, 50 ms mean latency
L = lam * W
print(f"Little's law: {lam:.0f} req/s x {W:.3f} s = {L:.0f} concurrent requests")
assert np.isclose(lam, L / W)                     # the law inverts consistently

# Batching: throughput rises toward 1/c1, per-request latency rises with the batch.
c0, c1 = 5.0, 1.0                                 # ms fixed overhead, ms per request
print("\n batch   throughput(req/s)   latency(ms)")
thru_prev, lat_prev = 0.0, 0.0
for b in [1, 8, 32, 64]:
    T = c0 + c1 * b                               # ms to process the batch
    thru = b / T * 1000                           # requests per second
    print(f" {b:5d}   {thru:14.0f}   {T:11.0f}")
    assert thru > thru_prev and T > lat_prev      # throughput up, latency up
    thru_prev, lat_prev = thru, T
print("\nbatching trades latency for throughput:", True)
```

The $p99$ latency sits far above the mean (the reason targets are written against
it), Little's law converts a throughput-and-latency target into a concurrency
requirement, and the batch sweep shows throughput climbing toward $1/c_1$ while
per-request latency climbs with it.

## Exercises

**Exercise 1.** A service measures a mean latency of $W = 40$ ms and must sustain a
throughput of $\lambda = 500$ requests per second. Using Little's law, find the
average concurrency $L$ the system must hold. Then, if a single replica can hold at
most $L = 8$ requests in flight, how many replicas are needed?

<details>
<summary>Solution</summary>

**Step 1.** Convert latency to seconds: $W = 40 \text{ ms} = 0.040$ s.

**Step 2.** Apply Little's law $L = \lambda W$:

$$
L = 500 \cdot 0.040 = 20 \text{ concurrent requests}.
$$

**Step 3.** Divide by the per-replica capacity and round up: $\lceil 20 / 8 \rceil = \lceil 2.5 \rceil = 3$ replicas.

So the service must carry $20$ requests in flight on average, which takes $3$
replicas at $8$ slots each ($24$ slots of headroom for the $20$ needed).

</details>

**Exercise 2.** With the batch cost model $T(b) = c_0 + c_1 b$, throughput is
$b / (c_0 + c_1 b)$. Show that throughput is strictly increasing in $b$ and
approaches the ceiling $1/c_1$ as $b \to \infty$. Then, for $c_0 = 5$ ms and
$c_1 = 1$ ms, find the smallest integer batch whose per-request latency $T(b)$
exceeds a $p99$ budget of $50$ ms.

<details>
<summary>Solution</summary>

**Step 1.** Write throughput as $g(b) = b / (c_0 + c_1 b)$ and differentiate with
the quotient rule:

$$
g'(b) = \frac{(c_0 + c_1 b) - b \cdot c_1}{(c_0 + c_1 b)^2} = \frac{c_0}{(c_0 + c_1 b)^2}.
$$

Since $c_0 > 0$, $g'(b) > 0$ for all $b$, so throughput strictly increases.

**Step 2.** Take the limit by dividing numerator and denominator by $b$:

$$
\lim_{b \to \infty} \frac{b}{c_0 + c_1 b} = \lim_{b \to \infty} \frac{1}{c_0/b + c_1} = \frac{1}{c_1}.
$$

The ceiling is $1/c_1$, reached as the fixed cost $c_0$ is amortized away.

**Step 3.** Solve $T(b) = 5 + b > 50$, giving $b > 45$. The smallest integer batch
that breaks the budget is $b = 46$, with $T(46) = 51$ ms.

</details>

**Exercise 3 (code).** A serving system has fixed batch overhead $c_0 = 4$ ms and
per-request cost $c_1 = 0.8$ ms. Sweep batch sizes and find the largest batch whose
per-request latency $T(b)$ stays at or below a $p99$ budget of $30$ ms, then report
the throughput it achieves. Verify with an assert that the chosen batch meets the
budget and the next batch up would break it.

<details>
<summary>Solution</summary>

```python
import numpy as np

c0, c1 = 4.0, 0.8          # ms fixed overhead, ms per request
budget = 30.0              # p99 latency budget in ms

batches = np.arange(1, 200)
T = c0 + c1 * batches               # ms to process a batch of each size
ok = T <= budget                    # batches that fit the budget
best = batches[ok].max()            # largest batch that meets the budget

T_best = c0 + c1 * best
thru = best / T_best * 1000         # requests per second
print(f"largest batch within {budget:.0f} ms = {best}, "
      f"T = {T_best:.1f} ms, throughput = {thru:.0f} req/s")

assert c0 + c1 * best <= budget                 # chosen batch meets the budget
assert c0 + c1 * (best + 1) > budget            # one larger would break it
```

The largest batch is $32$ ($T = 4 + 0.8 \cdot 32 = 29.6$ ms, within budget), and
$33$ would push $T$ to $30.4$ ms, over the line. That batch delivers about $1081$
requests per second, climbing toward the ceiling $1/c_1 = 1250$ req/s.

</details>

Autoregressive models complicate this picture, because each request is not one
forward pass but a *loop* of them, which the next lesson on
[LLM serving](llm-serving) takes on.
