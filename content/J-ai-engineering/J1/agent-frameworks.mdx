The [hand-written ReAct loop](react-loop) is maybe twenty lines, so why use a
framework? Because the twenty lines hide a long tail of details that frameworks like
LangChain have already solved: prompt formatting for each model, parsing tool calls
when the API does not return clean JSON, retries on malformed output, conversation
memory, streaming, and tracing. A framework is a packaging of that tail<FN n="1" />. Knowing
exactly which part of *your* loop each abstraction replaces is what lets you use one
without it becoming a black box.

## The abstractions, mapped to the loop

Every agent framework offers the same three core abstractions, each standing in for a
piece you wrote by hand:

- **Tool.** A decorator or wrapper that turns a plain function into a tool: it reads
  the function's signature and docstring to generate the schema you previously wrote
  out by hand. This replaces your manual tool registry.
- **Agent executor.** The object that *is* the loop: it owns the Thought-Action-
  Observation cycle, the model calls, the dispatch, and the step budget<FN n="2" />. This replaces
  your `for` loop and dispatcher.
- **Memory.** A store of conversation history that is automatically threaded back into
  the prompt each turn. This replaces the `history` list you passed around manually.

The same agent in framework form collapses to a few declarations (this is
illustrative, not runnable here):

```python-static
from langchain.agents import create_react_agent, AgentExecutor
from langchain.tools import tool

@tool
def get_stock(ticker: str) -> float:
    """Get the latest price for a stock ticker."""
    return prices[ticker]

agent = create_react_agent(llm, tools=[get_stock], prompt=react_prompt)
executor = AgentExecutor(agent=agent, tools=[get_stock], max_iterations=5)
executor.invoke({"input": "What is Apple trading at?"})
```

The `@tool` decorator generates the schema from the type hints and docstring,
`create_react_agent` wires the model to the tools, and `AgentExecutor` runs the loop
you wrote by hand, with `max_iterations` as the same step budget.

## What you gain and what you give up

The trade is real in both directions. You **gain** the solved tail: robust parsing,
retries, memory, streaming, swappable model backends, and an ecosystem of pre-built
tools. You **give up** transparency and control. When the agent misbehaves, the bug is
now inside the framework's prompt templating or output parser, layers you did not
write, and matching the framework's assumptions to your model can be its own work.

The judgment call: reach for a framework when you want the solved tail and your use
case fits its shape, and stay with the hand-written loop when you need to see and
control every token, which is common for latency-critical or high-stakes systems.

## Exercises

**Exercise 1.** For each of the three core abstractions (tool, agent executor,
memory), name the exact piece of the hand-written ReAct loop it replaces, and
state one detail the abstraction handles that the hand-written version left for
you to write.

<details>
<summary>Solution</summary>

**Step 1.** Map each abstraction to the loop piece it stands in for, taken
directly from the mapping in this lesson.

- **Tool** replaces the **manual tool registry**: the dict that paired each tool
  name with its function, schema, and parameter list.
- **Agent executor** replaces the **`for` loop plus dispatcher**: the Thought-
  Action-Observation cycle, the model calls, the routing to the right function,
  and the step budget.
- **Memory** replaces the **`history` list** you passed around by hand each turn.

**Step 2.** Name a detail each abstraction adds beyond the bare loop piece.

- Tool: it generates the JSON schema from the function signature and docstring,
  so the schema cannot drift out of sync with the function.
- Agent executor: it parses tool calls when the model does not return clean JSON
  and retries on malformed output.
- Memory: it threads the conversation history back into the prompt automatically,
  including any summarization or windowing the store applies.

</details>

**Exercise 2.** A team runs a customer-support agent in a regulated domain where
every model output must be logged verbatim and a compliance reviewer must be able
to trace why any given tool was called. They are choosing between a framework
executor and the hand-written loop. Argue which side the transparency requirement
pushes them toward, and name the one framework benefit they would forfeit.

<details>
<summary>Solution</summary>

**Step 1.** Identify the dominant requirement. The constraint is auditability:
verbatim logging plus a traceable reason for each tool call. The lesson notes that
with a framework "the bug is now inside the framework's prompt templating or output
parser, layers you did not write," so the reasoning that drove a tool call is
partly hidden inside abstractions the team does not control.

**Step 2.** Weigh it against the framework's gains. The framework buys the solved
tail (parsing, retries, memory, streaming, swappable backends). None of those
removes the audit problem; some (hidden prompt templating) make it worse.

**Step 3.** Conclude. The transparency requirement pushes them toward the
hand-written loop, where they see and control every token and can log the exact
prompt and the exact parsed call. What they forfeit is the solved tail: they must
write and maintain their own parsing, retries, and memory rather than inheriting
the ecosystem's.

</details>

**Exercise 3.** The lesson says a framework's *linear* executor "strains" once
control flow branches, loops back, or pauses for human input. Take a refund agent
that must: look up an account, then either issue a refund or escalate to a human,
and if it escalates, pause until the human approves. Explain why a single linear
Thought-Action-Observation loop cannot express this cleanly, and name the property
a graph-structured agent adds to fix it.

<details>
<summary>Solution</summary>

**Step 1.** Describe the control flow the task needs. After the account lookup the
agent must choose between two distinct paths (refund vs escalate), and one of those
paths must *stop* mid-run and wait for an external event (human approval) before
continuing.

**Step 2.** Show where a linear loop strains. A single Thought-Action-Observation
loop has one path: think, act, observe, repeat. Branching to two outcomes forces
the choice into conditionals smuggled inside the model's prompt or the dispatcher,
and there is no first-class place to *suspend* the loop and resume it later from
the same state. The control flow becomes an implicit tangle rather than an explicit
object.

**Step 3.** Name the fix. A graph-structured agent makes branching an explicit
router edge and makes pause/resume natural through checkpointing of the shared
state, so the escalate path can halt and resume on approval. That is exactly the
case the next lesson on [graph-structured agents](langgraph-state-machines) takes
up.

</details>

Either way, the loop underneath is the one from the last lesson. When control flow
gets more complex than a single loop, branching, looping back, pausing for human
input, even a framework's linear executor strains, which is the case for
[graph-structured agents](langgraph-state-machines).
