The [dbt mental model](J3/multi-source-ingestion), a transformation is a `SELECT`, models
reference each other to form a DAG, was the introduction. This lesson goes a level deeper
into the machinery that makes dbt the backbone of the data platform: `ref`-based
dependencies, materializations, and the tests-and-docs that turn a pile of SQL into a
maintained codebase.

## refs build the DAG automatically

A dbt **model** is a `.sql` file holding one `SELECT`. The key construct is that a model
refers to another not by hard-coding a table name but through `ref('other_model')`:

```python-static
-- models/customer_orders.sql
SELECT c.id, c.name, count(o.id) AS order_count
FROM {{ ref('stg_customers') }} c
LEFT JOIN {{ ref('stg_orders') }} o ON o.customer_id = c.id
GROUP BY 1, 2
```

Because every dependency is expressed as a `ref`, dbt reads the files and **infers the
dependency DAG** from them, no one maintains the graph by hand. It then runs models in
[topological order](I1/orchestration-dags) and, in production, inserts the right schema
names per environment. Raw inputs are declared as `source`s, so the DAG's roots are
explicit too. The result is a graph dbt can build, visualize, and trace end to end.

## Materializations: how a model becomes physical

The same `SELECT` can be made physical in different ways, chosen per model by its
**materialization**, and the choice trades freshness against compute:

- **View.** The model is a saved query, recomputed every time it is read. Zero storage,
  always fresh, but slow if queried often or built on heavy logic.
- **Table.** The model is rebuilt into a stored table on each run. Fast to query, but
  recomputes everything each run, expensive for large data.
- **Incremental.** Only *new or changed* rows are processed and appended each run. This is
  how dbt handles large, append-mostly data efficiently, the [idempotent](I1/orchestration-dags)
  partition logic of a pipeline, expressed declaratively.

Choosing materializations is the main performance lever in a dbt project: views for cheap
staging logic, tables for frequently-queried marts, incremental for the big event tables<FN n="1" />.

## Tests and docs make it a codebase

Two features turn transformations into maintained software. **Tests** are declarative
assertions on a model's output, declared in YAML: `unique` and `not_null` on a key,
`accepted_values` on an enum, `relationships` for referential integrity. They run in the
same pipeline, so a transformation that would violate an invariant fails the build instead
of silently corrupting a downstream mart, the [data-quality](I1/drift-detection) gate moved
into the transformation layer. **Documentation and lineage** are generated from the same
project: descriptions live beside the models, and because the DAG is known, dbt produces a
browsable lineage graph showing exactly which sources feed which marts.

Put together, `ref`-inferred DAG, per-model materializations, and built-in tests and docs,
dbt makes warehouse transformations version-controlled, tested, and traceable, which is why
it anchors the analytics-engineering workflow<FN n="2" />.

## Exercises

**Exercise 1.** A model `daily_active_users` is queried by a dashboard that refreshes every
few seconds, all day, and the underlying logic is a heavy aggregation over a large events
table. Pick a materialization for it and justify the choice against the freshness-versus-compute
tradeoff. What would you pick instead if the dashboard were read once a day?

<details>
<summary>Solution</summary>

**Step 1.** A view recomputes the heavy aggregation on every read. With reads arriving every
few seconds all day, that is the aggregation run thousands of times per day: maximum compute,
and slow per query. So a view is the wrong choice here.

**Step 2.** A table materializes the result once per run and serves stored rows on each read.
The dashboard then reads a precomputed table cheaply and fast; the cost is one rebuild per dbt
run, and staleness bounded by the run cadence. For a frequently-read mart, that is the standard
choice, so pick **table**.

**Step 3.** If the dashboard were read once a day, the per-read cost stops mattering. A single
view evaluation per day is cheaper than maintaining a stored table and is always fresh, so a
**view** becomes the better trade. The materialization choice follows the read/write ratio:
many reads favor table, few reads favor view.

</details>

**Exercise 2.** A teammate proposes hard-coding production table names inside each model's
`SELECT` instead of using `ref('other_model')`, arguing it is "more explicit." Name two
capabilities dbt would lose, and explain why each depends specifically on `ref`.

<details>
<summary>Solution</summary>

**Step 1.** dbt infers the dependency DAG by reading the `ref` calls in each file. Hard-coded
table names are opaque strings, so dbt can no longer tell which model feeds which. The
automatic DAG, and therefore correct topological build order, is lost: dbt could try to build
a model before its input exists.

**Step 2.** `ref` is also how dbt rewrites table names per environment (dev, staging, prod
schemas). A hard-coded production name points every environment at production, so a dev run
reads from and could clobber production tables. The environment isolation depends on dbt
controlling the name resolution, which it only does through `ref`.

**Step 3.** Lineage docs and `relationships` test wiring also ride on the inferred DAG, so
"explicit" hard-coding actually removes the explicit, machine-checkable lineage `ref` provides.
The string is more literal but less informative.

</details>

**Exercise 3.** An `orders` model should satisfy two invariants: `order_id` is unique and
never null, and every `customer_id` in it exists in the `customers` model. Map each invariant
to a dbt test, and explain what concretely happens to a pipeline run when a new upstream batch
introduces a duplicate `order_id`.

<details>
<summary>Solution</summary>

**Step 1.** Uniqueness and non-nullity of the key map to the `unique` and `not_null` tests
declared on `order_id` in the model's YAML. The cross-model existence requirement maps to a
`relationships` test pointing `customer_id` at `customers.id` (referential integrity).

**Step 2.** When an upstream batch introduces a duplicate `order_id`, the `unique` test runs
in the same pipeline as the build and finds more than one row per key, so the test fails. dbt
reports the failing test and the run is marked failed.

**Step 3.** Because the test gate sits in the transformation layer, the duplicate is caught
before any downstream mart consuming `orders` is trusted: the failure stops the bad data from
silently propagating, the same fail-fast posture a data-quality gate gives, moved into the
transformation step itself.

</details>

Transformations assume the data already
arrived correctly; guaranteeing *that* at the boundary is the job of
[data contracts](data-contracts).
